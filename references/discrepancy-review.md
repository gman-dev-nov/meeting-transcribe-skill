# Сверка двух транскриптов

Использовать этот контракт после `scripts/dual_transcribe.py run` для
русскоязычных записей. Скрипт уже сопоставил сырые GigaAM- и Whisper-артефакты
по времени и создал `<имя>.comparison.json`.

## Обязательные правила

1. Прочитать оба полных JSON-транскрипта, указанных в `transcripts`, и все
   элементы `candidates` из comparison JSON.
2. Считать `machine_signals` только подсказками. Самостоятельно оценить, меняет
   ли различие смысл.
3. Не выбирать правильную версию, не объединять тексты и не исправлять их по
   confidence, словарю или общим знаниям. Решение всегда остаётся человеку.
4. Для каждого без исключения `candidate_id` записать решение
   `discrepancy` или `same_meaning`. Не копировать тайм-коды и версии текста:
   команда `render` подставит авторитетные значения из comparison JSON,
   отклонит неизвестный ID, дубликат или неполное покрытие кандидатов.
5. Не создавать аудиоклип и не предполагать наличие плеера в чате. В результате
   указывать интервал исходной записи.
6. До ответа пользователя не представлять зависящие от расхождения решения,
   сроки, числа или цитаты как подтверждённые.

Игнорировать чистую пунктуацию, регистр, безопасные филлеры и разбиение одного
слова (`необязательно` / `не обязательно`), если смысл точно совпадает.
Остальные содержательные различия сохранять, даже если они кажутся легко
разрешимыми по контексту.

## Приоритеты

| Уровень | Когда ставить |
|---|---|
| `critical` | Меняется отрицание или модальность; решение, обязательство, исполнитель, срок, число/единица, условие или область действия; затронуты деньги, право, безопасность, приватность либо существенный риск. |
| `substantive` | Меняется фактический тезис, имя, сущность, технический термин либо присутствует смысловой пропуск, но нет немедленного риска неверного действия. |
| `minor` | Буквальная формулировка различается, однако смысл и все значимые сущности совпадают. Показывать только если человеку действительно может понадобиться дословная версия. |

Допустимые категории:

- `negation_or_polarity`
- `number_or_unit`
- `date_or_deadline`
- `name_or_entity`
- `decision`
- `commitment_or_action`
- `condition_or_scope`
- `risk_or_compliance`
- `technical_term`
- `meaningful_omission`
- `other_semantic`

## Review JSON

Взять `<имя>.review-template.json`, сохранить копию как
`<имя>.review.json` и заполнить `decisions` ровно одним решением для каждого
кандидата. Пустой неизменённый шаблон не проходит `render`, если кандидаты есть.

```json
{
  "schema_version": 1,
  "comparison_file": "/absolute/path/meeting.comparison.json",
  "decisions": [
    {
      "candidate_id": "D007",
      "verdict": "discrepancy",
      "severity": "critical",
      "categories": ["negation_or_polarity", "decision"],
      "review_reason": "Наличие отрицания меняет зафиксированное решение."
    },
    {
      "candidate_id": "D008",
      "verdict": "same_meaning",
      "review_reason": "Различаются только пунктуация и безопасный филлер."
    }
  ]
}
```

Не добавлять поля `preferred`, `selected`, `final_text`, `merged_text` или
`canonical_text`.

Проверить и отрендерить результат:

```bash
python3 scripts/dual_transcribe.py render "<имя>.review.json"
```

Команда создаст `<имя>.disagreements.json` и
`<имя>.disagreements.md`. Показать Markdown пользователю и попросить
прослушать каждый указанный интервал в исходной записи. Применять формулировку
только после ответа вида `D007: «правильный текст»`.

## После ответа человека

Сохранить ответы дословно в `<имя>.human-resolutions.json`: для каждого ответа
указать `candidate_id`, `confirmed_text` и `confirmed_by: "user"`. Не изменять
сырые `.gigaam.*` и `.whisper.*` артефакты. При частичном ответе оставить
остальные ID в состоянии `pending_human_review`; зависящие от них тезисы в
отчёте остаются неподтверждёнными. Окончательный `<имя>.report.md` строить по
подтверждённым формулировкам и явно перечислять нерешённые ID в метаданных.
