# Contributing

Спасибо за интерес. Скилл локальный, тестируется на реальных записях, поэтому
PR'ы приветствуются — особенно тесты на корнер-кейсах (длинные тишины,
плохое аудио, несколько языков подряд, 6+ спикеров).

## Локальная разработка

1. Клонируй и поставь зависимости по разделу [Установка](README.md#установка)
   из README. По умолчанию: `whisper.cpp` на Apple Silicon,
   `faster-whisper` на Linux/Windows/Intel Mac и GigaAM в отдельном venv для
   русского двойного прохода. Диаризация устанавливается опционально.
2. Из корня клона проверь окружение: `python3 scripts/setup_check.py` — wizard покажет, что
   установлено, чего не хватает и какими интерпретаторами будут запущены
   Whisper и GigaAM (см. `WHISPER_PYTHON` / `GIGAAM_PYTHON` в
   `references/setup.md`).
3. Для разработки держи клон в произвольной рабочей папке и подключи его
   симлинком. Из корня клона для Codex (приложение и CLI):

   ```bash
   mkdir -p "$HOME/.agents/skills"
   ln -s "$PWD" "$HOME/.agents/skills/meeting-transcribe"
   ```

   Для Claude Code вместо `~/.agents/skills` используй `~/.claude/skills`.
   Если по целевому пути уже есть скилл, сначала проверь его содержимое и
   сохрани локальные изменения. Открой новую сессию агента; если Codex не
   обнаружил скилл, перезапусти его.

   Команды `scripts/...` в этом документе запускаются из корня клона. При
   проверке установленного скилла из другой рабочей папки используй
   абсолютные пути из [README](README.md#использование-в-агенте).

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

Зависимостей и моделей не требуют: покрыты политика модели, сопоставление двух
транскриптов, контракт LLM-review, атомарная публикация артефактов и словарная
нормализация. Гонять их нужно и системным `python3` (на macOS это 3.9), и
свежим — в CI матрица 3.9/3.13. Транскрипцию на реальной записи проверяй
руками: `python3 scripts/dual_transcribe.py run "<файл>"`.

Для проверки интеграции Codex открой задачу в другой папке, явно вызови
`$meeting-transcribe` с абсолютным путём к тестовой записи и проверь полный
цикл: preflight, два независимых ASR-прохода, LLM-review по контракту,
рендеринг расхождений и отчёт после разрешения критических расхождений.
Используй отдельную папку для тестовых артефактов. Смысловую сверку выполняет
активная модель Codex, включая Astra при её доступности; модель в скилле
не фиксируется. ASR-модель остаётся `large-v3` / `quality` / beam=5.

`agents/openai.yaml` использует схему Codex: `interface` для метаданных UI
и `policy.allow_implicit_invocation` для автоматического выбора скилла.
`dependencies.tools` предназначен для MCP-сервисов; Python-пакеты, ffmpeg
и ASR-модели описываются в инструкции установки и проверяются
`setup_check.py`. Схема и пути установки:
[официальная документация Codex](https://learn.chatgpt.com/docs/build-skills).

## Что мы ценим в PR

- **Минимальный диф.** Один PR — одна тема. Не смешивай рефакторинг с фичей.
- **Воспроизводимый тест.** Если фиксишь баг — приложи короткий пример
  (фрагмент аудио или конкретный кейс), на котором было плохо. Проверим, что
  на нём теперь хорошо.
- **Без лишних зависимостей.** Скилл умышленно лёгкий: `ffmpeg` + один
  Whisper-бэкенд + опционально диаризатор. Новые внешние пакеты обсуждаем
  в issue до PR.
- **Русскоязычные комментарии и сообщения скрипта приветствуются.** Скилл
  заточен под русский, и пользователь читает stdout — пиши понятно и для
  него.

## Что в скоупе скилла

- Транскрипция и диаризация локальных аудио/видео в meeting-сценарии.
- Preflight-анализ файла (длительность, тишины, audio props, рекомендация
  бэкенда и флагов).
- Финальный отчёт по [`assets/report_template.md`](assets/report_template.md):
  TL;DR, темы, решения, action items, цитаты, открытые вопросы.

## Что вне скоупа

- Cloud-ASR (Whisper API, AssemblyAI, etc.) — намеренно. Скилл локальный:
  после загрузки моделей в сеть ходит только суточная анонимная проверка
  обновлений после отчёта, и та выключается `MEETING_TRANSCRIBE_NO_UPDATE_CHECK=1`.
- Телеметрия и любые идентификаторы установки — никогда, в том числе в
  проверке обновлений.
- Live-стриминг (real-time) — другой профиль задач.
- UI/виджеты — скилл предназначен под текстовый интерфейс агентного CLI (Claude Code, Codex и совместимые).

## Релизы

Проверка обновлений на стороне пользователя сравнивает файл `VERSION`
установленной копии с последним **релизом** на GitHub и показывает буллеты из
тела релиза. Поэтому релиз без заполненного тела равносилен отсутствию релиза:
пользователь увидит номер версии и ничего про то, что изменилось.

Порядок выпуска версии:

1. Перенести записи из `## [Unreleased]` в `CHANGELOG.md` в новую секцию
   `## [X.Y.Z] — ГГГГ-ММ-ДД`. Буллеты пишутся для человека, а не как пересказ
   коммитов — это ровно тот текст, который увидит пользователь.
2. Обновить `VERSION` (одна строка, без префикса `v`).
3. Влить в `main`, поставить тег `vX.Y.Z` и опубликовать релиз, взяв тело из
   соответствующей секции CHANGELOG:

   ```bash
   git tag -a v1.2.3 -m "1.2.3"
   git push origin v1.2.3
   gh release create v1.2.3 --title "1.2.3" --notes-file /path/to/release-notes.md
   ```

**Буллеты в теле релиза пишутся одной строкой каждый**, даже если в CHANGELOG
тот же пункт перенесён для читаемости. Тело релиза разбирает та копия скилла,
которая стоит у пользователя, а копии версии 1.0.0 умеют читать только первую
строку пункта: перенос там превратится в оборванную на середине фразу. Пока
такие копии в ходу, длина строки в теле релиза — не косметика.

Pre-release и draft пользователям не показываются: скилл читает
`releases/latest`, а тот их отсекает. Это удобный способ выпустить версию,
которую видят только тестировщики.

## Issues

Перед заведением — поищи похожее в трекере. В описании укажи:

- ОС и чип (`uname -sm`).
- Используемый Whisper-бэкенд.
- Длительность и характер записи (Zoom, телефон, диктофон, лекция).
- Что ожидалось vs что произошло.
- Если возможно — `python3 scripts/transcribe.py "<файл>" --analyze`
  (preflight-JSON) чтобы было видно профиль входа.
